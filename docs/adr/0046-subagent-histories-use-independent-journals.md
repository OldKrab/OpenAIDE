# Subagent Histories Use Independent Journals

Status: accepted

Each Subagent History is stored under its owning Task in an independently recoverable snapshot and journal pair, while the Task projection owns the Subagent summary tree, lifecycle, and committed history sequence. Spawn is committed before child output and terminal lifecycle after child output, preserving the ACP ordering contract without mixing every history into the Main Agent's Chat vector or coordinating unrelated child files in one rewrite. A missing or damaged child history reports that history as unavailable without quarantining the Task and Main Agent Chat.

Ordinary Task snapshots include the bounded Subagent summary tree but do not embed complete child histories. Selecting a Subagent loads its normalized history through an independently paged interface using the same message presentation shape as Chat.

Child journals accept the original full-history frames and three per-change frames: an Agent text append, a message upsert, and a plan change. A text append commits its message identity, role, new text, and resulting message metadata together. An upsert carries one complete message, which replaces the message with the same identity or is appended; a plan change carries the whole current plan or its absence. So streamed text, tool updates, permission outcomes, and plan changes cost one frame for the changed item instead of a rewrite of the preceding history. Compaction publishes a complete snapshot before replacing the journal; replay skips the already-materialized prefix after an interrupted compaction and discards only an unterminated final record after an interrupted append. Completed malformed records fail explicitly.

The per-change frames require history schema 2. A schema 1 history is first published as a schema 2 snapshot, so an App Server that understands only schema 1 refuses the history as unsupported and reports it unavailable instead of misreading its journal. A writer compacts once the journal holds 256 frames, or when the next frame would grow the journal beyond the larger of the snapshot size and 1 MiB. A journal that still holds full-history frames, or a prefix an interrupted compaction left, is published as the snapshot the first time it is loaded. A background pass at App Server start does the same for journals beyond that byte budget in histories nobody opens; it finds them by file size without reading them.

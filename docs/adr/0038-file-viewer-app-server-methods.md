# File Viewer App Server Methods

Status: accepted

Web and Desktop talk to App Server with `fileViewer/open` (originating absolute path and optional line), `fileViewer/openFromHandle` (handle plus relative href or fragment), `fileViewer/refresh`, and `fileViewer/release`. After that first open, Frontend never reads with a raw path. The snapshot result carries handle, display path, basename, UTF-8 text or an image preview (PNG, JPEG, WebP, GIF, bounded to 2048 pixels and 2 MiB, same inspection surface as Tool image preview) or a byte-free `pdf` kind or fallback/error, truncated flag, and optional language. VS Code does not use these methods.

For Web downloads (#401), the authenticated HTTP download route accepts `fileViewerHandle` with the initialized `clientInstanceId`. The existing viewer handle is reusable until release and remains bound to its owning client. `check=1` checks readability without returning file bytes, allowing the tab to report a failure before browser handoff. The transfer request reopens the current regular file, streams its bytes without preview limits, and sets an attachment filename from the referenced basename. Neither request accepts a raw path. Errors after browser handoff belong to the browser's download manager.

The snapshot `truncated` flag also identifies a reduced-resolution/static image preview. Frontend labels that preview explicitly; the original filesystem file and download handle are unaffected. File reads and conversion execute outside the shared protocol lock after authorization; completion rechecks client ownership before returning contents.

Project files adds task-authorized `fileViewer/listDirectory`, `fileViewer/search`, `fileViewer/changes`, and `fileViewer/diff`. App Server resolves the Task Workspace, then runs bounded filesystem/Git work outside the shared protocol lock. Discovery rejects traversal and canonical symlink escapes. Search is literal, respects ignore rules by default, and reports one-based content locations. Git review includes HEAD identity, working changes, old/new paths, and authoritative hunk line numbers; external diff drivers and text conversion are disabled. Non-repository, binary, conflict, limit, and failure states are explicit. Results are observations, not file capabilities; selected-file reads still use the existing viewer registry. Concrete limits and continuation/ignore semantics are documented in `app-server-protocol/src/project_files.rs`. Frontend supersedes obsolete requests; already-running work finishes within its bounds. Structured start/terminal events contain safe identifiers, operation, duration, and classified outcome.

With [ADR-0066](0066-project-files-belong-to-a-workspace-and-open-beside-chat.md) these four methods and `fileViewer/open` accept either a Task or a Project as the identity, never both; with a Project, an optional worktree id selects one worktree of that Project's repository and any other worktree is rejected. The existing containment, symlink, limit, and ignore rules apply unchanged to the resolved root. The change list reports added and removed line counts per file and the total number of changed files before paging. Changes and diff take a base: uncommitted work, or everything since the merge base with the default branch. The result names the default branch only when that comparison differs from uncommitted work, and a workspace without one answers `noDefaultBranch`, on which Frontend falls back to uncommitted work. The [rework plan](../plans/project-files-rework.md) records the slices.

# Desktop Updates have platform release and recovery keys

Each supported Desktop platform has one protected-CI Desktop Update Release Key for ordinary releases and one offline Desktop Update Recovery Key whose public half ships in the app. A product-owned update domain serves the version-aware Desktop Update Feed from GitHub Pages so installations that missed a key-transition release can receive a trusted bridge before later updates; GitHub Releases retains the immutable updater artifacts, which remain independently protected by platform code signing.

The feed offers one approved release to every eligible installation rather than assigning clients to randomized rollout buckets. Update checks disclose only channel, current version, platform, and architecture; OpenAIDE sends no installation identity or product data.

A Desktop release remains draft until both supported platform artifacts are platform-signed, updater-signed, and smoke-tested. Release publication makes those artifacts immutable; only a later atomic feed deployment makes the version eligible on both platforms. Native Desktop performs a cache-bypassed eligibility check immediately before installation and refuses an update that was withdrawn or cannot be revalidated online.

The feed starts with an explicitly versioned v1 endpoint and manifest. Existing field meanings remain stable and optional fields may be added, while a breaking schema change requires a new endpoint plus a bridge release that understands it; unknown required semantics fail closed.

The feed retains a source-version manifest for every publicly shipped update-capable release so dormant installations keep a route into the supported update graph. Updater artifacts remain required only while reachable as a current target, storage-compatibility bridge, or trust-recovery bridge; retaining a source manifest does not keep every historical release active as an update target.

Ordinary update discovery is a persistent in-app status, not an operating-system notification. V1 defines no forced, critical, or security-update urgency tier; adding one requires separately signed policy and interruption rules rather than trusting mutable feed presentation.

Feed traffic is restricted to the canonical HTTPS update domain. Artifact downloads accept only validated final destinations under the canonical repository's immutable GitHub Releases, plus a separately approved recovery origin if one is later established; redirects are revalidated and receive no credentials or custom authorization headers.

Each platform Recovery Key has two encrypted offline copies in separate controlled locations. OpenAIDE proves the recovery path with non-production artifacts and feed paths before the first production updater release, periodically afterward, and after release-infrastructure changes. Release Keys rotate only through a proven bridge when compromise, custody change, or cryptographic policy requires it, not merely because a calendar interval elapsed.

A reviewed, non-secret Desktop Update Graph in the repository is the source of truth for source version, channel, platform, next eligible target, compatibility evidence, and signing identity. CI rejects non-increasing or cyclic edges, unreachable bridges, missing evidence, and mutable or mismatched targets, then generates and validates the complete feed tree. A protected GitHub Pages deployment replaces that tree atomically; generated manifests are never hand-edited and a failed deployment leaves the previous complete feed active.

The first platform-signed updater-capable Desktop release is a one-time manual installation because earlier clients contain neither updater code nor trusted public keys. Production feed activation waits for the official domain and protected deployment, platform signing and notarization, Release and Recovery Key custody plus recovery drill, proven Update Edges, signed and installed-app-tested artifacts for both platforms, forced failure and interruption evidence including safe macOS replacement, accessible UI verification, and diagnostics redaction review. Until those gates pass, builds expose updates as unavailable and make no production feed request.

Updater tests may compile an isolated test configuration containing an ephemeral signing key and local HTTPS feed. Production builds contain only the official feed and trusted public keys: they expose no environment-variable, command-line, hidden-setting, or renderer-controlled override for endpoints or trust material. Installed prerelease validation uses the protected prerelease feed and normal platform signing rather than enabling a production endpoint override.

Before either production platform feed advances, the exact signed source and target installers must pass on real supported Windows and macOS machines. Evidence covers discovery and Release Notes, download/cancel/retry, active work and competing App Shell clients, withdrawal and offline revalidation, signature/digest/size/disk/redirect failures, shutdown-barrier abort, installer interruption and recovery, relaunch receipts, Windows passive progress, macOS bundle replacement, and accessible wide and narrow UI behavior. Both platforms pass before the feed changes for either platform.

Delivery proceeds in trust order: define the Update Graph, manifest schema, signing automation, and isolated test feed; implement the native state machine, verification, receipt, and shutdown barrier; compose the shared Settings UI; prove exact Update Edges; then complete signed installed-app tests and the Recovery Key drill. The production feed is activated only after the complete evidence set passes.

# Native Desktop owns update execution

The native Rust Desktop shell exclusively owns Desktop Update feed access, trusted keys, artifact verification, downloaded bytes, progress, and installation; Frontend can request fixed update operations and render sanitized state but cannot provide URLs, signatures, keys, or updater configuration. A verified download becomes Ready to Update, and only explicit Restart and Update consent invokes the existing App Server-owned coherent shutdown contract before installation and relaunch; OpenAIDE never installs first and asks for restart afterward.

Ready to Update is process-scoped in v1. Native Desktop keeps the verified artifact in its private cache, retains its verified digest in process memory, checks the exact bytes again before installation, and removes the artifact when it is applied or the process exits; a later process downloads again. Remote Release Notes render only restricted text Markdown without raw HTML, images, or manifest-supplied links; the fixed GitHub release action derives its destination from validated release identity.

Background-check failures remain silent in product UI, while manual-check failures are visible. Network failure returns to Update Available with explicit retry; verification failure deletes the bytes and blocks installation without bypass. Download can be cancelled and partial bytes are removed; native Desktop reports size, enforces a bounded artifact, and checks temporary capacity before downloading. Before installation it persists only an Update Attempt Receipt containing previous version, target version, and timestamp, and the next launch compares that receipt with the running version before reporting one-time success or an incomplete update.

OpenAIDE reports Updated only after the target native binary and bundled App Server versions match, App Server initializes and opens the primary state root, and Frontend becomes interactive. Restart and Update during active work offers only Stop Work and Update or Cancel; v1 does not persist an instruction to update automatically after work finishes.

Native Desktop exposes one typed process-scoped update snapshot with unavailable, idle, checking, available, downloading, ready-to-update, applying, and failed states plus stable classified errors and bounded progress metadata. Exactly one operation exists per process, concurrent checks coalesce, and repeated intents are idempotent. Automatic checking starts only after Frontend is interactive. Development and unsigned preview builds remain unavailable and never contact the production feed.

The WebView receives no generic Tauri updater capability. Its narrow native command surface can only check, download the currently offered update, cancel that download, or request Restart and Update; no command accepts a URL, signature, key, version, header, or updater configuration. Structured updater diagnostics contain safe operation identity, versions, channel, platform, outcome, duration, attempt and byte counts, and stable error class, while excluding release content, trust material, artifact data, URLs, redirects, paths, proxy details, and free-form errors.

Desktop exposes update detail through a capability-gated Application updates section in App General Settings, while the existing Settings affordance gains a textual Update available status for discovery and opens that section. macOS additionally provides its conventional Check for Updates application-menu command; Windows uses shared Settings. After validated relaunch, one quiet accessible Updated to vX notice can open Release Notes without changing the restored Task route. Progress and state use semantic, throttled announcements, text plus icon status, visible keyboard focus, responsive layout, and reduced-motion behavior.

Native Desktop persists only automatic-attempt and successful-check timestamps for scheduling. It checks after interactive startup no more than once per 24 hours with small random jitter and bounded failure backoff, while explicit Check for Updates bypasses cadence and backoff without creating a concurrent operation.

Windows applies the per-user NSIS updater in passive mode after OpenAIDE completes coherent shutdown. The user sees only a small non-interactive native progress window before automatic relaunch, never an installer wizard or elevation prompt.

macOS applies a verified safe replacement of the signed application bundle after coherent shutdown, without reopening a DMG or installer surface, then relaunches through the same receipt validation. Production enablement remains gated on pinning and forced-failure testing an updater implementation that restores the prior bundle on every failed or interrupted replacement. Unsigned, read-only, DMG-launched, non-writable, or otherwise unsupported installations remain unavailable with a specific manual recovery action and never request elevation from inside OpenAIDE.

The updater plugin and its Rust dependency graph are pinned by the release lockfile. Any updater dependency change repeats the installed destructive-failure matrix, including permission failure, interrupted replacement, damaged package, launch failure, and recovery; unit tests alone cannot qualify that dependency change for production.

Frontend observes native update state through the Desktop shell adapter as full snapshots with a process-local monotonic revision. Each change publishes a complete replacement, and Frontend ignores older revisions rather than reconstructing state from independently ordered progress or error events; this shell lifecycle contract does not enter App Server Protocol.

Installation additionally requires App Server-owned Update Shutdown Readiness. Another initialized App Shell client blocks the update and is never force-disconnected; stale clients use normal reconnect-grace expiry. Every Desktop-owned native and WSL App Server must drain accepted work, mark storage clean, release its writer lock, and terminate as one update shutdown barrier, while failure to reach the barrier cancels installation and leaves the current Desktop release authoritative.

That barrier has prepare, commit, and abort phases. Every runtime first enters a temporary quiescing state that rejects new work without exiting; native Desktop commits termination only after all runtimes prepared, while any failure releases every prepared runtime back to service. Cancellation remains available until the user confirms Stop Work and Update and commit begins; after commit, applying is non-cancellable and work remains disabled until installer handoff or a barrier abort restores normal operation. The Update Attempt Receipt is persisted only after all committed shutdowns complete and immediately before installer launch.

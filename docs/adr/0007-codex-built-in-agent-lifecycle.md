# Built-In Agent Lifecycle

OpenAIDE is ACP-only for the current product direction, and Codex and OpenCode are built-in Agents. Agent definitions contain identity and launch information only; auth methods come from ACP `initialize.authMethods`, and Configuration Options come from session setup and update messages.

For Codex, OpenAIDE owns and tests one exact `@openaide/codex-acp` version per release. The first explicit Codex demand installs that locked dependency graph into durable per-user OpenAIDE storage with npm, validates it, and publishes it atomically; later launches execute the managed entrypoint directly through Node.js. A `codex-acp` executable found on `PATH` is never selected for the built-in Agent, and installation never falls back to `npx`, a system package, an older managed version, or an unvalidated partial directory. Users who need a different adapter build register it as a Custom Agent. OpenCode retains its existing `opencode acp` / `npx -y opencode-ai acp` launch policy until a tested OpenCode pin is adopted separately.

App Server coalesces concurrent installation demand across processes and owns the ephemeral Installing Agent Status. New Task preparation, Task Navigation, and Agent Settings render **Installing the Codex integration…** from that shared state. Passive Native Session Discovery does not provision Codex; a successful explicit install resumes the waiting lifecycle and requests discovery reconciliation. A missing Node.js/npm prerequisite produces setup-required Agent Status, while download, validation, launch, or ACP initialization failure produces failed Agent Status with explicit retry. Product surfaces never expose npm, paths, registry URLs, environment values, or raw output, while diagnostics record safe classified start and terminal events. The Agent is selectable for new Tasks after successful ACP initialization and while it has no known auth/setup blocker; a real Prepared Task or Task operation may subsequently reveal `auth_required` and pause work for explicit authentication. Task-specific Configuration Options are discovered from each Task's Native Session after `task/create`; if Task session setup fails, OpenAIDE shows renderable Task preparation error state instead of falling back to a mock.

App Server owns the structured setup reason and retry result. Shared Frontend owns the product explanation and action layout, while each App Shell advertises and performs only the external-link, reload, or equivalent recovery actions it supports; shared product state does not hard-code VS Code commands.

OpenAIDE does not guess Configuration Option defaults. A controlled no-options state is allowed only when the Agent successfully reports no Configuration Options or the Task session exposes an explicitly recoverable no-options state.

After a user completes Agent auth or setup in settings, OpenAIDE attempts to reconnect automatically. Agent settings also exposes an explicit retry action so users can rerun connection/setup checks when auto reconnect fails or external state changes.

Built-in Agents are fixed product entries, not editable templates. Each built-in exposes enable/disable, setup/auth, probe, retry, and status actions; users who need a different command, arguments, or environment create a Custom Agent instead.

The first production transport is ACP over stdio because current built-ins use process stdio. Custom Agents in the first iteration also use stdio process transport. Other ACP transports, including HTTP/WebSocket draft transport, remain tracked planned support and do not block built-in ACP Agent support.

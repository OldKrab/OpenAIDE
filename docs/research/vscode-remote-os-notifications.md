# OS notifications from VS Code remote extensions

Research date: 2026-08-03

## Conclusion

Native OS notifications from a VS Code extension are not a normal extension-API feature. The supported notification APIs (`showInformationMessage`, `showWarningMessage`, and `showErrorMessage`) render inside the VS Code workbench, and VS Code's UX guide explicitly describes them as appearing in the bottom-right of VS Code, not in the host operating system's notification center ([API capabilities](https://code.visualstudio.com/api/extension-capabilities/common-capabilities#display-notifications), [notification UX guide](https://code.visualstudio.com/api/ux-guidelines/notifications)). An OpenAI Codex extension maintainer states the limitation directly: VS Code has no standard desktop-notification API for extensions; it only exposes an in-VS-Code toast, without an audible signal ([maintainer comment](https://github.com/openai/codex/issues/3962#issuecomment-3813918231)).

Remote development makes direct platform commands the wrong abstraction. A workspace extension executes inside SSH, WSL, a Dev Container, or Codespaces, while the desktop and its notification service are on the local UI host. VS Code warns that Node APIs and shell scripts execute where the extension host runs and may fail remotely; UI extensions run locally, workspace extensions remotely ([remote-extension architecture](https://code.visualstudio.com/api/advanced-topics/remote-extensions#architecture-and-extension-kinds)). Thus `notify-send`, PowerShell, `osascript`, or `node-notifier` launched from a workspace extension target the remote environment, not reliably the user's desktop. WSL-to-Windows PowerShell is a special-case bridge, not a general Remote SSH/container solution.

The production-grade shape is therefore a **local presenter plus a remote event source**. That can be one deliberately local UI extension paired with a workspace/router extension, or a separate desktop companion. A single workspace extension that switches among platform commands is only correct for local workspaces.

| **Remote Notifier** | Purpose-built example of the split design: a `ui`-side main extension receives events and invokes SnoreToast, `terminal-notifier`, or `notify-send`; a workspace-side Router runs in SSH/WSL/containers, exposes a loopback HTTP endpoint, and installs `code-notify` ([publisher architecture](https://marketplace.visualstudio.com/items?itemName=ddyndo.remote-notifier#how-it-works)). ## Viable designs for OpenAIDE

1. **Best fit: two-extension presenter/router.** Keep task lifecycle detection with the workspace-side OpenAIDE extension/App Server. Send a small typed event to an OpenAIDE UI companion forced to `"extensionKind": ["ui"]`; the companion invokes the local platform notification backend. VS Code commands can cross local/remote extension-host boundaries even though exported extension APIs cannot, which makes a private command a supported transport between the two halves ([cross-host command guidance](https://code.visualstudio.com/api/advanced-topics/remote-extensions#communicating-between-extensions-using-commands)). This is the same essential architecture as Remote Notifier without its terminal-facing HTTP surface.

2. **Desktop companion.** If OpenAIDE already has or plans a local desktop process, publish lifecycle events to it and let it own OS integration, permissions, click activation, icons, sound, and notification grouping. Cline's menubar/hub design demonstrates this pattern. It also works outside VS Code, but adds installation and process-lifecycle costs.

3. **Webview sound plus VS Code toast.** This is the simplest no-companion fallback and works across Remote SSH/WSL/containers because VS Code routes its own API and renders webviews locally. Roo Code demonstrates the audio half. It still is not an OS notification and may be suppressed by workbench settings, window suspension, or audio policy.

4. **Hooks / terminal sequences.** Expose trustworthy `task-complete`, `input-required`, and `approval-required` hooks so advanced users can integrate their own notifier. BEL and OSC are useful fallbacks, but VS Code's current BEL is primarily a visual/accessibility signal, and its OSC 99 implementation explicitly stays inside VS Code ([terminal bell settings](https://github.com/microsoft/vscode/blob/7bc425de76bd97411173e3464d6f20c3dd6455e7/src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts), [OSC 99 handler](https://github.com/microsoft/vscode/blob/7bc425de76bd97411173e3464d6f20c3dd6455e7/src/vs/workbench/contrib/terminalContrib/notification/browser/terminalNotificationHandler.ts)). Hooks also inherit the host-location problem: a hook running under SSH or in a container cannot directly notify the local desktop.

## Recommendation

Treat OS notifications as a distinct local presentation integration, not as a smarter `notify-send` switch. Keep VS Code toasts as the baseline and add a local presenter only if native notifications are a product requirement. For VS Code Remote support, use a small UI companion and cross-host command/event bridge; make local OS permission/focus failures visible through a “Test system notification” command and logs. Do not claim Remote SSH, WSL, or Dev Container support from platform-command auto-detection alone.

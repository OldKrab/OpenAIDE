# Desktop signing and zero-cost update distribution

## Question

How do comparable open-source desktop projects sign Windows and macOS releases,
and what release/update policy is realistic for OpenAIDE when the cash budget is
strictly **$0**?

Research was checked on 2026-08-28. Claims below use project-owned source,
workflows, documentation, or platform-vendor documentation. "Unknown" means the
public primary sources do not establish the fact.

## Conclusion

OpenAIDE should treat three controls as separate:

1. **Tauri updater signatures** authenticate update bytes to an already-installed
   OpenAIDE build. They are mandatory in Tauri and can be operated for $0.
2. **Windows Authenticode** establishes a Windows-recognized publisher. A
   self-signed certificate behaves like no signature in SmartScreen.
3. **Apple Developer ID plus notarization** establishes a macOS-recognized
   publisher. Self-signed and ad-hoc signatures do not satisfy Gatekeeper for
   public distribution.

At absolute $0, OpenAIDE cannot satisfy ADR 0055's production activation gate on
both supported platforms: SignPath may solve Windows if it accepts the project,
but there is no verified free Developer ID/notarization route for an individual
open-source project. The decisive policy is therefore to keep production Desktop
updates unavailable on **both** platforms, continue manual GitHub Release installs,
finish only the ADR's isolated implementation/evidence work, and apply to SignPath.
Do not route around the accepted gate through ad-hoc self-update, a package
manager, or a different shell.

## Updater signatures are not OS code signing

Tauri's updater requires a public/private signing-key pair, verifies the entire
download before installation, and does not allow this verification to be
disabled. Losing the private key prevents future updates to installed clients.
This signature is generated by Tauri and is distinct from Authenticode and Apple
Developer ID signing.

Source: [Tauri updater — Signing updates](https://v2.tauri.app/plugin/updater/#signing-updates).

## Can a once-approved ad-hoc macOS app update without another prompt?

**Not as a reliable product contract.** A particular installation may update and
relaunch without another Gatekeeper prompt, but neither Apple nor Tauri guarantees
that behavior for replacement unsigned/ad-hoc bundles.

### Verified behavior

- Apple says **Open Anyway** saves the app as an exception so it can be opened
  later. Apple does not say that replacing the bundle with different unsigned or
  ad-hoc code inherits that exception. [Apple — Open a Mac app from an unknown
  developer](https://support.apple.com/en-gb/guide/mac-help/mh40616/mac).
- Apple defines the designated requirement (DR) as the identity macOS uses to
  recognize an updated version as the same code. Unsigned code has no DR; an
  ad-hoc DR is tied to that specific code version, so macOS cannot reliably track
  identity across versions. [Apple TN3127 — Inside Code Signing:
  Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements),
  [Apple — Code Signing Requirement Language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html).
- Gatekeeper checks downloaded software and tracks provenance of files written by
  downloaded software. Apple also explains that background self-update downloads
  generally are not quarantined because quarantine is opt-in for non-sandboxed
  apps. That explains a possible prompt-free update; it is not a promise that the
  replacement is trusted or will remain prompt-free. [Apple Platform Security —
  Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web),
  [Apple WWDC19 — Advances in macOS Security](https://developer.apple.com/videos/play/wwdc2019/701/).
- Tauri verifies the downloaded archive against its updater public key, then its
  macOS installer extracts the archive and renames the replacement bundle into
  place. The source contains no step that preserves a Gatekeeper exception,
  establishes a stable Apple identity, or performs a Gatekeeper assessment.
  [Tauri updater source](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs).
- OpenAIDE currently pins `tauri-plugin-updater` 2.10.1. The upstream repository
  has an open destructive-failure report against 2.10.0/current `v2`: after moving
  the installed app into a self-deleting temporary backup, a failed final rename
  can leave neither old nor new app installed; the privileged path deletes the
  old bundle before moving the replacement. The reported sequence is visible in
  the same current source. This independently fails ADR 0055's interruption and
  recovery requirements. [OpenAIDE dependency](../../apps/desktop/src-tauri/Cargo.toml),
  [Tauri issue 3505](https://github.com/tauri-apps/plugins-workspace/issues/3505),
  [Tauri updater source](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs).
- Tauri's distribution guide warns that ad-hoc signing still requires users to
  whitelist an installation in Privacy & Security. [Tauri — macOS Code Signing](https://v2.tauri.app/distribute/sign/macos/#ad-hoc-signing).

### Bounded inference

An in-app Tauri download may lack quarantine metadata, so the replacement can
appear to work without another prompt on a tested machine. That outcome depends
on OS version, sandbox/provenance behavior, installation path, permissions, and
enterprise policy. It is an incidental path around a Gatekeeper evaluation, not
evidence that the old manual exception transferred to the new code. A real-machine
test can prove one update edge on one OS build; it cannot create the stable code
identity that Apple says unsigned/ad-hoc code lacks.

Sparkle reinforces the distinction rather than supplying contrary evidence. It
supports EdDSA update signatures but still recommends Developer ID signing and
notarization, and it contains explicit quarantine/Gatekeeper handling. Sparkle's
extra machinery is absent from the Tauri replacement path and is not a guarantee
for unsigned Tauri updates. [Sparkle documentation](https://sparkle-project.org/documentation/),
[Sparkle security and reliability](https://sparkle-project.org/documentation/security-and-reliability/),
[Sparkle source](https://github.com/sparkle-project/Sparkle).

**Decision:** dependable, no-repeat Gatekeeper UX requires every source and target
release to use a stable Developer ID identity and notarization. ADR 0055 already
requires signed installed-app testing and safe macOS replacement, so this finding
supports rather than conflicts with the ADR. Replacing Tauri's macOS install
routine with a proven atomic/rollback-safe implementation is required before
activation, but it would solve only replacement safety; it cannot make unsigned
code inherit a stable Gatekeeper identity.

Microsoft documents that a self-signed Windows certificate has the same
SmartScreen behavior as no signature. Even a new valid OV/EV certificate may
warn until it builds reputation; a consistent trusted identity lets reputation
carry across releases.

Source: [Microsoft — SmartScreen reputation for Windows app developers](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

Apple says public direct distribution requires a Developer ID certificate from
an Apple Developer Program member and notarization. Apple's code-signing guide
states that self-signed identities do not work for Gatekeeper. Tauri likewise
warns that ad-hoc signing still requires users to whitelist the app in Privacy &
Security.

Sources: [Apple — Developer ID](https://developer.apple.com/support/developer-id/),
[Apple — Understanding the Code Signature](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html),
[Tauri — macOS Code Signing, Ad-Hoc Signing](https://v2.tauri.app/distribute/sign/macos/#ad-hoc-signing).

## OpenAIDE at an absolute $0

### Windows direct downloads: apply to SignPath

SignPath Foundation provides its certificate and SignPath.io service free for
accepted open-source projects. Its published conditions require an OSI-approved
license, no proprietary project components or commercial dual licensing, an
active and already released project, documented functionality, MFA, explicit
author/reviewer/approver roles, a privacy statement, a visible code-signing
policy, trusted-build origin verification, and manual approval of releases.
Acceptance remains discretionary and includes a fuzzy reputation assessment.

Source: [SignPath Foundation conditions](https://signpath.org/terms.html) and
[free OSS service](https://signpath.org/).

OpenAIDE is public, AGPL-3.0-only, active, and has releases, so it appears to meet
the basic license/activity/release conditions. It is **not application-ready**:
the current README still says Desktop is planned, and the repository has no
privacy policy or SignPath-format code-signing policy. Before applying, document
the actual desktop download, network/privacy behavior, signing scope, and named
roles; audit every packaged binary against SignPath's own-binary/upstream-binary
rules. SignPath alone decides eligibility.

If accepted, sign the OpenAIDE executable and project-owned PE sidecars before
NSIS packaging, then sign the installer, and make absence of either signature a
release-blocking failure. Users will see `SignPath Foundation` as publisher, not
`OpenAIDE`, and a new certificate can still need time to acquire SmartScreen
reputation.

### Microsoft Store: free account, but no shortcut for the current installer

Microsoft's current onboarding has no registration fee for either Individual or
Company accounts. Store-distributed MSIX packages receive Microsoft signing and
hosting for free. However, an EXE/MSI submission must already be signed with a
CA-trusted Authenticode certificate; Microsoft does not re-sign it. Tauri's
current Store guide generates only EXE/MSI and explicitly requires the linked
installer to be code-signed. Therefore a free Store account does **not** make the
current OpenAIDE NSIS installer trusted for $0.

Sources: [Microsoft — developer account](https://learn.microsoft.com/en-us/windows/apps/publish/faq/open-developer-account),
[Microsoft — Store packaging](https://learn.microsoft.com/en-us/windows/apps/publish/get-started),
[Microsoft — MSI/EXE requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/app-package-requirements),
[Tauri — Microsoft Store](https://v2.tauri.app/distribute/microsoft-store/).

A custom MSIX packaging track could obtain free Store signing, but that is a
separate packaging/install/update design, not a signing toggle. Do not add it
unless Store distribution itself is a product requirement. If SignPath accepts
OpenAIDE, the signed NSIS route can also satisfy the signing prerequisite for a
Store-linked EXE after its offline/silent-install requirements are met.

for one platform would conflict with ADR 0055's current single cross-platform
publication/feed decision. That is a possible future ADR change, not a workaround
authorized by this research.

### macOS: no public-trust path at $0 for an individual project

Apple's fee waiver is limited to qualifying legal entities that are nonprofits,
accredited educational institutions, or government bodies. It expressly excludes
individuals, sole proprietors, and single-person businesses. Developer ID public
distribution otherwise requires paid Apple Developer Program membership. No
current evidence establishes that OpenAIDE is owned by a qualifying entity.

Source: [Apple Developer Program fee waiver](https://developer.apple.com/help/account/membership/fee-waivers/).

Apple's current membership comparison limits the free account to development and
personal testing; Developer ID, notarization, and distribution require the $99
annual program. Apple's official program overview lists the organizational fee
waiver but no open-source-specific sponsored membership or signing program.
Therefore OSS status alone supplies no current free Apple signing path. A
third-party promise to lend credentials would not be an Apple-documented program
and is not acceptable trust-key custody for OpenAIDE.

Sources: [Apple — Choosing a Membership](https://developer.apple.com/support/compare-memberships/),
[Apple — Programs overview](https://developer.apple.com/help/account/membership/programs-overview),
[Apple — Get Started](https://developer.apple.com/get-started/).

At $0, OpenAIDE may continue distributing an unsigned or ad-hoc-signed DMG with
accurate warning/whitelisting instructions. Ad-hoc signing is useful on Apple
Silicon but does not remove Gatekeeper intervention. A homemade certificate adds
no public trust and should not be shipped as if it did.

### Policy for unsigned-build updates

Every published updater artifact should still carry a valid Tauri updater
signature; this prevents a compromised mirror or manifest from substituting
bytes. But updater verification does not create a Windows/macOS publisher
identity or prove that the replacement will pass the OS's policy.

OpenAIDE's accepted update design already requires unsigned builds to expose
updates as unavailable and make no production feed request; production activation
also waits for platform signing and notarization. That is stricter than merely
disabling installation after discovery and should remain the controlling policy.

Source: [ADR 0055 — Desktop Updates have platform release and recovery keys](../adr/0055-desktop-updates-have-platform-release-and-recovery-keys.md).

For stable releases:

- expose the updater as **unavailable** and make no production feed request on
  unsigned/ad-hoc builds;
- allow in-app download/install only when the target artifact has both a valid
  Tauri updater signature and the platform's production OS signature;
- never weaken TLS, Tauri signature verification, or OS checks to make an
  unsigned update appear seamless;
- show the artifact's signing state in the UI and diagnostics.

This policy sacrifices even in-app update discovery on macOS at $0, but avoids
teaching the app to bypass the platform trust decision. A separately isolated
test configuration may exercise automatic replacement of ad-hoc builds on owned
machines; it is not a supported public-distribution guarantee.

## Security and UX tradeoffs

- **Manual unsigned macOS install:** costs nothing and keeps the native product,
  but Apple explicitly warns that overriding Gatekeeper is a common malware path.
  Every instruction asking users to click Open Anyway spends product trust and
  may be prohibited by managed-device policy.
- **Automatic ad-hoc replacement:** Tauri's signature gives strong update-byte
  authenticity, but a prompt-free relaunch may depend on the replacement escaping
  quarantine rather than passing Gatekeeper. That is worse than an honest manual
  warning because the user no longer sees the OS trust decision.
- **External package managers:** hashes, scanning, and predictable CLI upgrades
  are useful defense in depth, but they split support and recovery across another
  release channel and do not establish OpenAIDE's OS publisher identity.
- **Store/PWA/local-web pivots:** can obtain convenient $0 updates only by changing
  packaging ownership or removing native Desktop boundaries. They add migration,
  dual-install, data-location, capability, support, and rollback questions that
  are much larger than the updater feature.
- **Keeping ADR 0055 closed:** means Windows users also wait even if SignPath is
  approved, because the ADR intentionally publishes neither platform until both
  pass. The cost is delayed convenience; the benefit is one release decision,
  one recovery graph, and no lower-trust platform path.
- **One-time manual Windows approval is not universal:** Smart App Control can
  block unknown unsigned code and applies signature checks to executable files
  regardless of whether they came from a browser. Enterprise App Control can
  likewise require an explicit publisher, catalog, hash, or managed-installer
  allow rule. A Tauri updater signature is invisible to these Windows controls,
  so a "works for most users" path would knowingly exclude protected consumer
  and managed devices and would still contradict ADR 0055's platform-signing
  gate. [Microsoft — Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview),
  [Microsoft — SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation),
  [Microsoft — Application Control](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/appcontrol).

## Decisive recommendation at absolute $0

**Do not activate production in-app Desktop updates on either platform.** Keep
ADR 0055 unchanged: builds expose updates as unavailable and make no production
feed request until Windows and macOS artifacts are both platform-signed,
updater-signed, smoke-tested, and all recovery/evidence gates pass.

Continue distributing manual GitHub Release installers with accurate signing
status and macOS Gatekeeper instructions. In parallel, complete the isolated
Tauri updater implementation and Recovery/Release Key drills, prepare and submit
the SignPath application for Windows, and leave the production feed dark. Do not
ship an unsigned/ad-hoc macOS self-updater, do not use Homebrew/WinGet to claim the
gate is solved, and do not replace Desktop with npm/PWA solely to obtain updates.

The activation condition is singular: fund one Apple Developer membership or
move ownership to a legitimately eligible fee-waiver entity, then Developer
ID-sign, notarize, staple, and pass the exact installed-app update edges required
by ADR 0055 alongside SignPath-signed Windows artifacts. Until then, manual update
friction is the honest consequence of the $0 constraint.
